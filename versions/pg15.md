# PostgreSQL 15 Security Notes

## Summary

PostgreSQL 15 is one of the most significant security releases in the project's history. The revocation of `CREATE` privilege on the `public` schema from `PUBLIC` — a default that had existed for decades — closes a long-standing privilege escalation and search_path hijacking risk. Released in October 2022.

---

## 1. `public` Schema `CREATE` Privilege Revoked (MAJOR BREAKING CHANGE)

### The Old Behaviour (PG 14 and Earlier)
In all PostgreSQL versions prior to 15, the pseudo-role `PUBLIC` was granted `CREATE` and `USAGE` on the `public` schema by default. This meant that any role with a database connection could create tables, functions, operators, or types in the `public` schema.

**Attack scenario (pre-PG15):** A low-privileged tenant role creates a trojan function named `lower()` in the `public` schema. When a superuser or `SECURITY DEFINER` function with an unsafe `search_path` calls `lower()`, PostgreSQL resolves the trojan version first, executing arbitrary code in an elevated privilege context.

### The New Behaviour (PG 15+)
- Only the **database owner** can create objects in the `public` schema.
- `PUBLIC` retains `USAGE` privilege (can reference existing objects) but no `CREATE`.

### Check if Your Database Retained the Old Grant (After Upgrade)
```sql
-- Check if PUBLIC still has CREATE on public schema
SELECT has_schema_privilege('public', 'public', 'CREATE') AS public_has_create;
-- If true, your database was upgraded and the old grant survived

-- Check ACL directly
SELECT nspname, nspacl
FROM pg_namespace
WHERE nspname = 'public';
-- Look for '=UC' entries (= means PUBLIC, UC = USAGE + CREATE)
```

### Remediation for Upgraded Databases
```sql
-- Revoke CREATE from PUBLIC on public schema
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- Verify
SELECT has_schema_privilege('public', 'public', 'CREATE');
-- Must return: false
```

### Impact Assessment
```sql
-- Find objects in public schema owned by non-superuser, non-DBA roles
SELECT 
    c.relname AS object_name,
    c.relkind AS object_type,
    pg_get_userbyid(c.relowner) AS owner,
    r.rolsuper AS owner_is_superuser
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_roles r ON r.oid = c.relowner
WHERE n.nspname = 'public'
  AND NOT r.rolsuper
  AND r.rolname NOT IN ('postgres')
ORDER BY c.relkind, c.relname;
```

## 2. `security_invoker` Views

PostgreSQL 15 added the `security_invoker` option for views, which changes how permission and RLS checks are evaluated:

| Mode | Permissions Checked Against | RLS Applied For |
|------|-----------------------------|-----------------|
| `SECURITY DEFINER` (default) | View owner | View owner (bypasses caller's RLS) |
| `security_invoker = true` | View caller | Caller's identity |

### Creating a `security_invoker` View
```sql
CREATE VIEW customer_summary
WITH (security_invoker = true) AS
SELECT id, name, email FROM customers;

-- Any RLS policies on 'customers' are evaluated for the caller, not the view owner
```

### Auditing Views That May Bypass RLS
```sql
-- Find views on RLS-enabled tables that DON'T use security_invoker
SELECT 
    v.schemaname AS view_schema,
    v.viewname AS view_name,
    t.schemaname AS table_schema,
    t.tablename AS table_name,
    t.rowsecurity AS table_has_rls,
    v.definition
FROM pg_views v
JOIN pg_tables t ON v.definition ILIKE '%' || t.schemaname || '.' || t.tablename || '%'
WHERE t.rowsecurity = true
  AND v.definition NOT ILIKE '%security_invoker%'
  AND v.schemaname NOT IN ('pg_catalog', 'information_schema');
```

## 3. `MERGE` Statement and RLS

PostgreSQL 15 introduced the SQL standard `MERGE` statement. An important security consideration: **RLS policies must explicitly handle `MERGE`**, as it performs `INSERT`, `UPDATE`, and `DELETE` under a single statement.

```sql
-- Example: Ensure MERGE targets are covered by ALL policy type
CREATE POLICY tenant_merge_policy ON accounts
    FOR ALL
    TO app_role
    USING (tenant_id = current_setting('app.tenant_id')::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
-- 'FOR ALL' covers SELECT, INSERT, UPDATE, DELETE, and MERGE
```

## 4. Logical Replication Improvements

- Improved `pg_publication_tables` visibility and filtering.
- Row filters and column lists for publications reduce data exposure in logical replication.

```sql
-- Audit what publications expose (column lists narrow exposure)
SELECT 
    p.pubname,
    pt.schemaname,
    pt.tablename,
    pt.attnames AS published_columns,  -- NULL means all columns
    pt.rowfilter
FROM pg_publication p
JOIN pg_publication_tables pt ON pt.pubname = p.pubname;
-- Any NULL in published_columns means ALL columns are replicated
```

## 5. Breaking Changes Affecting Security

| Change | Upgrade Action Required |
|--------|------------------------|
| `public` schema `CREATE` revoked from `PUBLIC` | Application roles may need explicit `GRANT CREATE ON SCHEMA app_schema TO app_role` |
| Views no longer transparently bypass RLS by default with `security_invoker` | Review views on RLS tables; consider adding `WITH (security_invoker = true)` |
| `MERGE` now available — RLS policies need `FOR ALL` or explicit `MERGE` coverage | Audit all RLS policies to ensure `MERGE` operations are covered |
| `pg_stat_activity.query_id` column added | No security impact; enables better query tracking |

---

## Verification Checklist for PG15 Environments

- [ ] `public` schema `CREATE` privilege has been revoked from `PUBLIC`
- [ ] All views accessing RLS-enabled tables have been reviewed for `security_invoker` appropriateness
- [ ] RLS policies cover `MERGE` operations where application uses `MERGE`
- [ ] Logical replication publications use column lists and row filters to minimize data exposure
- [ ] Application roles have been granted explicit `CREATE` on their intended schemas (not `public`)
- [ ] `pg_publication_tables` is audited to ensure no sensitive columns are unnecessarily published
