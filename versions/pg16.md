# PostgreSQL 16 Security Notes

## Summary

PostgreSQL 16 fundamentally redesigned the `CREATEROLE` privilege to close a long-standing privilege escalation path, added new predefined roles for connection management, and introduced logical replication from standbys. Released in September 2023.

---

## 1. `CREATEROLE` Privilege Redesign (MAJOR SECURITY FIX)

### The Old Behaviour (PG 15 and Earlier)
A role granted `CREATEROLE` could:
- Create new roles and modify non-superuser roles' passwords
- Grant itself or others membership into **any non-superuser role** (including roles with `BYPASSRLS`, `REPLICATION`, `pg_execute_server_program`, etc.)
- Effectively escalate privileges to any non-superuser level without constraint

This made `CREATEROLE` nearly equivalent to `SUPERUSER` in practice.

### The New Behaviour (PG 16+)

**Rule 1:** A role with `CREATEROLE` can only grant membership in roles for which it holds the `ADMIN OPTION`.

**Rule 2:** A role with `CREATEROLE` cannot alter or drop roles that it did not create (unless it holds appropriate `ADMIN OPTION`).

**Rule 3:** Only superusers can modify superuser accounts.

### Detection: Who Has `CREATEROLE` and What Can They Grant?
```sql
-- Find all CREATEROLE roles
SELECT rolname, rolsuper, rolcreaterole, rolcanlogin
FROM pg_roles
WHERE rolcreaterole = true
ORDER BY rolsuper DESC, rolname;

-- Find which roles have ADMIN OPTION (can grant others into those roles)
SELECT 
    r.rolname AS holder,
    g.rolname AS can_grant_into,
    m.admin_option
FROM pg_auth_members m
JOIN pg_roles r ON m.member = r.oid
JOIN pg_roles g ON m.roleid = g.oid
WHERE m.admin_option = true
ORDER BY r.rolname, g.rolname;
```

### Migration Impact
If your code relies on a `CREATEROLE` role managing existing role memberships, you must now:
1. Grant the managing role explicit `ADMIN OPTION` on the target roles it needs to manage:
```sql
GRANT target_role TO managing_role WITH ADMIN OPTION;
```

## 2. New Predefined Roles

### `pg_use_reserved_connections` (PG16+)
Allows a role to use connection slots reserved by the `reserved_connections` parameter. Without this, only superusers can use reserved slots.

```sql
-- Grant to monitoring or on-call DBA accounts
GRANT pg_use_reserved_connections TO on_call_dba;

-- Audit members
SELECT r.rolname
FROM pg_auth_members m
JOIN pg_roles g ON m.roleid = g.oid AND g.rolname = 'pg_use_reserved_connections'
JOIN pg_roles r ON m.member = r.oid;
```

### `pg_create_subscription` (PG16+)
Allows creating logical replication subscriptions without superuser privileges. Reduces the need for superuser grants in replication automation.

```sql
-- Audit who can create subscriptions
SELECT r.rolname
FROM pg_auth_members m
JOIN pg_roles g ON m.roleid = g.oid AND g.rolname = 'pg_create_subscription'
JOIN pg_roles r ON m.member = r.oid;
```

## 3. Logical Replication from Standby Servers

PostgreSQL 16 allows logical replication subscriptions to source from a physical standby server rather than the primary, reducing primary load and allowing read replicas to act as logical replication sources.

### Security Considerations
- The standby must be granted equivalent logical replication permissions to the primary.
- Subscription connection strings in `pg_subscription.subconninfo` may store credentials.

```sql
-- Audit subscription connection details (may contain credentials)
SELECT subname, subenabled, subconninfo
FROM pg_subscription;
-- Ensure subconninfo uses SSL (sslmode=verify-full) and SCRAM auth
```

## 4. `pg_hba.conf` Enhancements

PostgreSQL 16 added **regular expression support** for database and user name matching in `pg_hba.conf`:

```
# Allow users matching pattern 'app_.*' to connect using SCRAM
hostssl  all  +/^app_.*/  10.0.0.0/8  scram-sha-256
```

Also added the `require_auth` client parameter, allowing clients to mandate a specific auth method and reject connections if the server doesn't use it:
```bash
psql "host=db1 require_auth=scram-sha-256" 
```

---

## 5. Breaking Changes Affecting Security

| Change | Impact |
|--------|--------|
| `CREATEROLE` privilege scope narrowed | Scripts that relied on `CREATEROLE` for role management need `ADMIN OPTION` grants |
| `pg_create_subscription` new predefined role | Subscription creation no longer requires superuser |
| `require_auth` client parameter | Allows clients to enforce server auth method — should be used in production |
| COPY from `pg_hba_file_rules` improved parsing | More columns; error column for malformed rules |

---

## Verification Checklist for PG16 Environments

- [ ] All `CREATEROLE` roles are audited — none should have unexpected `ADMIN OPTION` grants
- [ ] `pg_use_reserved_connections` is granted only to emergency/on-call accounts
- [ ] `pg_create_subscription` is granted only to replication automation accounts
- [ ] Standby-based logical replication connections use `sslmode=verify-full`
- [ ] Application connection strings use `require_auth=scram-sha-256`
- [ ] `pg_hba.conf` regex patterns are carefully reviewed — avoid overly broad regex
- [ ] `reserved_connections` is set alongside `pg_use_reserved_connections` grants
