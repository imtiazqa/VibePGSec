# PostgreSQL 17 Security Notes

## Summary

PostgreSQL 17 brought native incremental backups, `LOGIN` event triggers for connection-time security enforcement, SQL/JSON improvements, and several security-relevant GUC changes. Released in September 2024.

---

## 1. Native Incremental Backup (`pg_basebackup --incremental`)

### What Changed
PostgreSQL 17 introduced built-in incremental base backups using WAL summary files. Previously, incremental backup required third-party tools (pgBackRest, Barman, WAL-G).

```bash
# Create a full base backup (reference point)
pg_basebackup -h localhost -U repl_user -D /backup/base --wal-method=stream

# Create an incremental backup from the manifest of the last backup
pg_basebackup -h localhost -U repl_user -D /backup/incr1 \
  --incremental=/backup/base/backup_manifest --wal-method=stream

# Combine backups for restoration
pg_combinebackup /backup/base /backup/incr1 -o /restore/combined
```

### Security Implications
- More frequent, shorter backup windows reduce data exposure during backup
- `backup_manifest` files contain file checksums — store these securely
- Incremental backup credentials still need the `REPLICATION` attribute or `pg_basebackup` role

```sql
-- Verify backup user has minimum required privilege
SELECT rolname, rolreplication, rolsuper
FROM pg_roles
WHERE rolname = 'backup_user';
-- rolreplication should be true; rolsuper should ideally be false
```

## 2. `LOGIN` Event Triggers

### What Changed
PostgreSQL 17 added support for event triggers that fire on the `login` event — meaning they execute as part of the connection authentication process, **after** the user authenticates but **before** any queries run.

### Security Use Cases
- Enforce IP-based restrictions at the SQL level (supplementing `pg_hba.conf`)
- Enforce time-of-day access controls
- Reject connections from deprecated application versions
- Log connection metadata beyond what `log_connections` provides
- Enforce multi-factor session setup (e.g., require setting application context variables)

```sql
-- Example: Block connections from unexpected application names
CREATE OR REPLACE FUNCTION enforce_application_name()
RETURNS event_trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
AS $$
BEGIN
    IF current_setting('application_name') NOT IN ('webapp', 'analytics', 'backup_tool') THEN
        RAISE EXCEPTION 'Connection rejected: unrecognized application_name "%"',
            current_setting('application_name');
    END IF;
END;
$$;

CREATE EVENT TRIGGER block_unknown_apps
ON login
EXECUTE FUNCTION enforce_application_name();
```

### Caution: Lock-Out Risk
A buggy `LOGIN` trigger can prevent **all** users from connecting, including administrators. Always test in a development environment first. Emergency recovery requires starting PostgreSQL with `--event-triggers=off`.

```sql
-- Audit existing login event triggers
SELECT evtname, evtevent, evtowner::regrole, evtenabled, evttags
FROM pg_event_trigger
WHERE evtevent = 'login';

-- Temporarily disable a misbehaving login trigger
ALTER EVENT TRIGGER block_unknown_apps DISABLE;
```

## 3. SQL/JSON Security Improvements

PostgreSQL 17 added SQL-standard JSON functions (`JSON_TABLE`, `JSON_EXISTS`, `JSON_QUERY`, `JSON_VALUE`) with improved type safety. Applications parsing JSON from user input should use these type-safe functions rather than custom parsing:

```sql
-- Safe JSON value extraction with type enforcement
SELECT JSON_VALUE(user_input::json, '$.role' RETURNING text) AS user_role;
-- Returns NULL if not a string, rather than throwing an injection-prone error
```

## 4. Security-Relevant GUC Changes in PG17

| Parameter | Change | Security Impact |
|-----------|--------|----------------|
| `wal_level` default | Still `replica` | No change |
| `track_wal_io_timing` | New parameter | Enables WAL I/O tracking for performance/audit |
| `allow_alter_system` | New parameter | Allows disabling `ALTER SYSTEM` entirely — **new hardening option** |

### Disabling `ALTER SYSTEM` (New Hardening Option)
`ALTER SYSTEM` allows any superuser to permanently modify `postgresql.conf` from a SQL session. In environments where configuration should only change through infrastructure-as-code (Terraform, Ansible), you can now disable it:

```ini
# postgresql.conf — requires restart
allow_alter_system = off
```

```sql
-- Verify
SHOW allow_alter_system;
```

---

## 5. Breaking Changes Affecting Security

| Change | Impact |
|--------|--------|
| `LOGIN` event triggers | Misconfigured triggers can lock out all users |
| `allow_alter_system` parameter | Environments using `ALTER SYSTEM` for config management must update workflows |
| `pg_combinebackup` required for incremental restores | Backup tooling must be updated |
| JSON functions return `NULL` on type mismatch instead of error | Application error handling behaviour changes |

---

## Verification Checklist for PG17 Environments

- [ ] Incremental backup procedures tested with `pg_combinebackup`; `backup_manifest` stored securely
- [ ] `LOGIN` event triggers are tested in dev/staging before production deployment
- [ ] Emergency runbook exists for disabling `LOGIN` triggers if they cause lock-out
- [ ] `allow_alter_system = off` is evaluated for production environments where config is managed via IaC
- [ ] Backup roles use `REPLICATION` attribute rather than `SUPERUSER`
- [ ] SQL/JSON functions are used in preference to string-based JSON parsing in application queries
- [ ] Event trigger ownership and `SECURITY DEFINER` usage is audited
