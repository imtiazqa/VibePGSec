# PostgreSQL 18 Security Notes

## Summary

PostgreSQL 18 introduces native OAuth 2.0 / OAUTHBEARER authentication, a new fine-grained `MAINTAIN` privilege for maintenance operations, native UUIDv7 generation (time-ordered, safe for public IDs), and virtual generated columns. Released in 2025.

---

## 1. `MAINTAIN` Privilege (New Fine-Grained Privilege)

### What Changed
Prior to PG18, running maintenance operations (`VACUUM`, `ANALYZE`, `REINDEX`, `CLUSTER`, `REFRESH MATERIALIZED VIEW`) on a table required the role to be the **table owner** or a **superuser**. This forced teams to either grant ownership to maintenance automation scripts (a security risk) or run maintenance as superuser.

PostgreSQL 18 introduces the `MAINTAIN` privilege: a dedicated table-level privilege that grants maintenance capabilities without data access or ownership.

```sql
-- Grant MAINTAIN to a dedicated maintenance role
CREATE ROLE db_maintenance WITH LOGIN PASSWORD 'SecureMaintenancePass';
GRANT MAINTAIN ON TABLE orders TO db_maintenance;
GRANT MAINTAIN ON ALL TABLES IN SCHEMA public TO db_maintenance;

-- Set for future tables in a schema
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT MAINTAIN ON TABLES TO db_maintenance;

-- Verify MAINTAIN grants
SELECT grantee, table_schema, table_name, privilege_type
FROM information_schema.table_privileges
WHERE privilege_type = 'MAINTAIN'
ORDER BY table_schema, table_name;
```

### Security Benefit
- Maintenance automation (cron jobs, Kubernetes CronJobs) no longer needs superuser access
- Separation of duty between data access roles and maintenance roles
- `MAINTAIN` cannot be used to `SELECT`, `INSERT`, `UPDATE`, or `DELETE` data

## 2. OAuth 2.0 / OAUTHBEARER Authentication

### What Changed
PostgreSQL 18 adds native support for **OAuth 2.0 Bearer Token** authentication via the `oauthbearer` authentication method in `pg_hba.conf`. Clients can authenticate using JWT tokens issued by an external identity provider (Okta, Entra ID / Azure AD, Keycloak, Google IAP).

### `pg_hba.conf` Configuration
```
# Require OAuth Bearer tokens from a specific issuer for remote connections
hostssl  appdb  all  10.0.0.0/8  oauthbearer  issuer=https://accounts.example.com scope=postgres
```

### Security Benefits
| Benefit | Detail |
|---------|--------|
| No static database passwords | Tokens are short-lived (typically 15–60 minutes) |
| Centralized identity management | User provisioning and deprovisioning via IdP |
| Token revocation | Immediately revoke access by revoking token at IdP |
| Short-lived credentials | Reduces blast radius from credential exposure |
| MFA enforcement | Apply MFA at the IdP level transparently |

### Security Risks
| Risk | Mitigation |
|------|-----------|
| Token theft (man-in-the-middle) | Enforce `hostssl` — never `host` with `oauthbearer` |
| Token expiry gaps | Configure short token lifetimes (≤15 min) |
| Clock skew validation | Ensure server NTP sync for `exp` claim validation |
| Issuer validation | Always set `issuer=` to a specific, trusted URL |

```sql
-- Verify OAuth configuration
SELECT name, setting FROM pg_settings
WHERE name LIKE 'oauth%';
```

## 3. UUIDv7 — Safer Public Identifiers

### What Changed
PostgreSQL 18 adds a native `uuidv7()` function generating **time-ordered UUIDs** per RFC 9562. Unlike UUIDv4 (random), UUIDv7 is monotonically increasing, making it B-tree index friendly while also being safe for use as public-facing identifiers.

### Security Relevance
UUIDv4 has been recommended over sequential integers for public-facing IDs to prevent **Insecure Direct Object Reference (IDOR)** attacks:

```sql
-- Using UUIDv7 for safe public identifiers
CREATE TABLE orders (
    id uuid DEFAULT uuidv7() PRIMARY KEY,
    customer_id uuid NOT NULL REFERENCES customers(id),
    amount numeric NOT NULL
);

-- UUIDv7 vs UUIDv4 for security:
-- UUIDv4: Fully random — safe against enumeration but poor index performance
-- UUIDv7: Time-ordered — same IDOR protection, better index performance
SELECT uuidv7();
-- e.g., 0192d3f8-5a3b-7c4d-a1b2-c3d4e5f60718
```

## 4. Virtual Generated Columns

PostgreSQL 18 adds **virtual generated columns** — values computed on-the-fly from other columns without being stored. Unlike stored generated columns (PG12+), virtual generated columns don't occupy disk space.

### Security Consideration
Virtual generated columns that derive sensitive data from other columns (e.g., combining first name + last name) are still subject to column-level privilege checks. Ensure `SELECT` is not granted broadly on tables with sensitive derived columns.

```sql
CREATE TABLE employees (
    id int PRIMARY KEY,
    salary_base numeric,
    bonus_pct numeric,
    -- Virtual: computed but not stored
    total_compensation numeric GENERATED ALWAYS AS (salary_base * (1 + bonus_pct)) VIRTUAL
);

-- Restrict access to the computed column
REVOKE SELECT (total_compensation) ON employees FROM app_readonly;
```

## 5. Breaking Changes Affecting Security

| Change | Impact |
|--------|--------|
| `MAINTAIN` privilege introduced | Maintenance scripts should be migrated from superuser to MAINTAIN-granted roles |
| `oauthbearer` auth method | `pg_hba.conf` format changes; token validation libraries required on server |
| `uuidv7()` built-in | Applications can migrate from `uuid_generate_v4()` (requires `uuid-ossp`) to built-in |
| Virtual generated columns | Column-level privilege model applies — audit grants on tables with virtual columns |

---

## Verification Checklist for PG18 Environments

- [ ] Maintenance automation roles use `GRANT MAINTAIN` instead of `SUPERUSER` or table ownership
- [ ] If `oauthbearer` is deployed: `hostssl` is enforced (never plain `host`)
- [ ] OAuth issuer URL is pinned to a specific, trusted identity provider
- [ ] Token lifetimes are configured to ≤15 minutes at the IdP
- [ ] UUIDv7 is used for public-facing entity identifiers (replacing sequential integers)
- [ ] Virtual generated columns with sensitive derived data have appropriate column-level privilege restrictions
- [ ] `DEFAULT PRIVILEGES` are configured for `MAINTAIN` on new schemas
